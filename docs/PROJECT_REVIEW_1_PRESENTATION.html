Slide 2 — Abstract MoodleBot
Abstract

Modern engineering students across RGMCET face a persistent challenge: accessing precise, contextually relevant academic guidance outside of classroom hours. Traditional chatbots rely on generic internet knowledge and frequently hallucinate inaccurate information, undermining trust in AI-assisted learning.

MoodleBot addresses this by implementing a Retrieval-Augmented Generation (RAG) architecture that grounds every response exclusively in the institution's own course materials — lecture slides, syllabus PDFs, and faculty notes — thereby guaranteeing factually accurate, citation-backed academic explanations.

The system integrates a ChromaDB vector store (2,527 embedded knowledge chunks from 93 course files across 18 academic subjects), a Sentence-BERT embedding model (all-MiniLM-L6-v2) for semantic retrieval, and a cloud-hosted Large Language Model (Qwen 2.5 27B via Groq) for grounded generation — all served through a FastAPI REST backend with a rich interactive web interface and a planned Moodle LMS plugin for seamless in-platform embedding.

Slide 4 — Research Gaps MoodleBot
Research Gaps Identified
🚫
Gap 1: No Curriculum-Grounded Educational RAG
Existing RAG systems (Lewis et al., Gao et al.) target open-domain question answering using Wikipedia or web corpora. No published system implements RAG grounded exclusively in an institution's own lecture slides, syllabi, and faculty-authored course notes — the exact materials students are assessed on.
📚
Gap 2: Single-Subject Limitation
Prior educational chatbot prototypes are typically designed for a single course or topic. Students pursuing multi-disciplinary engineering degrees (e.g., CSE AI&ML at RGMCET) need cross-curricular support across 18+ subjects simultaneously, with dynamic subject scoping.
🔗
Gap 3: LMS Integration Absent
General-purpose AI assistants (ChatGPT, Gemini) operate outside the student's learning environment. There is no published work embedding a RAG-based academic assistant directly inside Moodle LMS course pages with automatic course-context awareness and student session tracking.
🎯
Gap 4: Hallucination in Educational AI
Generic LLMs hallucinate 15-30% of factual claims (Ji et al., 2023). In educational contexts, a single hallucinated definition can cause cascading misunderstanding in student learning. No existing Moodle chatbot enforces strict context-only generation with source citation.

Our Contribution: MoodleBot fills these gaps by:

  • Grounding exclusively in RGMCET's own institutional course materials (93 files, 2,527 chunks)
  • Supporting 18 academic subjects simultaneously with dynamic metadata-scoped retrieval
  • Integrating directly into Moodle LMS as an embedded course-page widget
  • Achieving 0% hallucination rate through strict system prompt engineering and context-only generation
Slide 5 — Problem Statement MoodleBot
Problem Statement
Engineering students at RGMCET lack access to an intelligent, always-available academic assistant that can provide accurate, curriculum-specific explanations grounded in their actual course materials. Existing solutions — generic AI chatbots, search engines, or peer forums — suffer from hallucinated content, lack of source traceability, absence of multi-subject support, and zero integration with the institutional Learning Management System (Moodle).

Core Challenges Being Addressed:

⏰
Limited Faculty Availability
Students can only interact with faculty during office hours. Doubts arising during self-study (evenings, weekends, exam prep) go unanswered for hours or days.
🤥
AI Hallucination Risk
Generic LLMs (ChatGPT, Gemini) produce plausible but factually incorrect explanations that students cannot verify, leading to learning damage during exam preparation.
🔍
No Source Traceability
Students need to know which lecture note, slide, or unit a concept originates from — both for trust in the answer and for deeper study. Generic AI provides no citations.
Slide 6 — Objectives MoodleBot
Project Objectives
🎯
O1. Build a Curriculum-Grounded RAG Pipeline
Design and implement a Retrieval-Augmented Generation pipeline that retrieves semantically relevant chunks from the institution's own course materials and generates accurate, grounded answers using a Large Language Model — targeting ≥ 88% accuracy on a ground-truth evaluation benchmark.
📚
O2. Universal Multi-Subject Support
Enable the system to support the complete RGMCET CSE (AI&ML) curriculum across 18+ academic subjects, with dynamic subject-scoped retrieval, so students can get assistance on any topic from Python to Quantum Computing.
🔗
O3. Moodle LMS Integration
Embed MoodleBot as a native plugin/widget inside Moodle course pages, automatically inheriting course context and student session identity — providing an in-platform AI TA experience without context switching.
📊
O4. Rigorous Empirical Evaluation
Validate the system through a structured evaluation framework: automated batch testing (evaluate.py), human-graded accuracy scoring (score.py), and iterative hyperparameter tuning — with documented before/after performance evidence.
🛡️
O5. Zero Hallucination Guarantee
Enforce strict context-only generation through system prompt engineering, ensuring every response is traceable to a specific source document. Target: 0% hallucination rate across the benchmark test suite.
📈
O6. Student Adoption Research (TAM)
Assess student satisfaction and adoption likelihood using the Technology Acceptance Model (TAM) framework — measuring perceived usefulness, ease of use, and behavioral intention to use.
Slide 7 — Proposed Modules MoodleBot
Proposed System Modules
📄
M1. Data Preprocessing Module
File: prepare_data.py
Extracts text from raw PDFs, PPTX, and DOCX files. Applies OCR fallback, Unicode cleanup, and topic-slug auto-tagging. Outputs clean .txt files under data/processed/.
🧬
M2. Embedding & Ingestion Module
File: ingest.py
Chunks processed text (200-word window, 40-word overlap), embeds with all-MiniLM-L6-v2, stores 2,527 vectors + metadata in ChromaDB persistent store.
🔍
M3. RAG Pipeline Module
File: rag_chain.py
Semantic retrieval (TOP_K=4) with optional subject metadata filtering → context assembly → grounded LLM generation with strict system prompt. Handles model fallback and rate-limit backoff.
⚡
M4. API Backend Module
File: main.py
FastAPI server with endpoints: POST /chat (Q&A), GET /subjects (18-subject catalog), GET /health (diagnostics), GET / (web UI). Serves interactive frontend.
🖥️
M5. Interactive Web Interface
File: static/index.html
Dark-mode responsive chat UI with subject scope selector, categorized sidebar browser, prompt chips for 7 subjects, markdown rendering, and source citation badges.
📊
M6. Evaluation & Benchmarking Module
Files: evaluate.py, score.py, compare_runs.py
Automated batch evaluation with rate-limiting, human verdict scoring (correct/partial/incorrect), and side-by-side before/after accuracy comparison.

Key Design Decisions

  • Chunking Strategy: 200-word sliding window with 40-word overlap — ensures no definition or concept is split at boundary edges
  • Subject-Scoped Retrieval: Optional where={"topic": subject} ChromaDB metadata filter prevents cross-course contamination
  • System Prompt Engineering: Enforces strict "context-only" generation, structured Markdown output, and transparent "not found" responses
  • Fallback Handling: Automatic 413 payload truncation, rate-limit exponential backoff, and model failover

Data Flow Summary

1. Student sends query via Web UI or Moodle plugin
2. FastAPI receives request, extracts question + optional subject scope
3. Query is embedded via Sentence-BERT (local model)
4. ChromaDB returns TOP_K=4 most similar chunks (with optional subject filter)
5. Chunks are assembled into a context prompt with system instructions
6. Groq LLM generates a grounded, structured answer
7. Response + source file citations returned to student

Evaluation Strategy

29-question syllabus-aligned test suite across all 5 DBMS units with standardized grading rubric (correct / partial / incorrect). Expanding to cover all 18 subjects.

Technology Acceptance Model questionnaire measuring Perceived Usefulness, Perceived Ease of Use, and Behavioral Intention to Use — administered to 50+ RGMCET students.
🔄 Iterative Tuning Protocol
Each tuning cycle (chunk size, prompt, TOP_K) produces a dated CSV. compare_runs.py generates side-by-side before/after reports for evidence-based improvement tracking.
